# Code conventions

Read this before writing or reviewing code. It says how Atlas code is shaped; the [system design](../architecture/system-design.md) says what the boundaries are. When you change a convention, change this file in the same PR.

Agents copy the code nearest to them. Before you add a helper, pattern or file, find the existing way to do it and use that. If there are two ways, consolidate them rather than adding a third. The [reference implementations](#reference-implementations) are the shapes to copy.

## Core (Go)

### Layout

```text
core/
  cmd/atlas-core/          process wiring only: configuration, open, serve, signals
  cmd/atlasctl/            local CLI: parse arguments, call internal/management
  internal/api/            generated by oapi-codegen from protocol/openapi.yaml; never edit
  internal/app/            composition root and HTTP adapter: middleware, handlers, error rendering
  internal/<module>/       one package per responsibility in the system outline
  internal/<module>/internal/db/   sqlc queries private to that module
  internal/problem/        Protocol-visible errors returned by modules
  internal/storage/        shared SQLite opening, migrations and constraint helpers
  internal/management/     local administration shared by the CLI and TUI
```

### Modules own behavior and data

- A module exports a small type with ordinary methods, such as `entities.Service`. Callers use those methods. Nothing outside the module reads its tables.
- Module queries live in `internal/<module>/queries.sql` and generate into `internal/<module>/internal/db`. The Go `internal` rule then makes them unreachable from other packages. Do not add queries to another module's file.
- Tables are created by numbered migrations per database: `internal/storage/migrations/<database>/NNNN_<change>.sql`. sqlc reads the same directory as its schema. Never edit an applied migration; add another one.
- A module constructor takes its collaborators as arguments. Do not use package-level state or `init` side effects.
- Business rules live in the module, including resource-specific authorization such as "an Asset may report only for itself". Handlers never decide domain outcomes.

### HTTP handlers are thin

A handler does three things: read the caller from the context, call one module method, and convert the result to the generated success response.

- Return failures as `nil, err`. The shared strict-handler error hook renders `*problem.Error` values and logs everything else as an internal error. Do not build 4xx response literals in handlers.
- No SQL, JSON parsing, URL matching or validation in handlers or middleware.
- Routing is generated. Middleware never inspects `r.URL.Path` to choose behavior. A route that cannot be generated (such as a WebSocket upgrade) is registered explicitly by method and path next to the generated routes, with a comment explaining why.

### Protocol owns shape, access and limits

- Shape validation belongs in `protocol/openapi.yaml`: required fields, types, enums, formats, lengths, ranges, patterns and `additionalProperties: false`. Core enforces it with the generated spec through the request-validation middleware. Handwritten Go and TypeScript never repeat a Protocol enum, range or pattern.
- Modules validate only rules the schema cannot express, such as "latitude and longitude together" or "the Dataset must be current".
- Access is declared per operation in Protocol. Each kind of caller is its own bearer security scheme (`operator`, `asset`, ...), and an operation lists the kinds that may call it: `security: [{operator: []}, {asset: []}]`. The middleware authenticates the credential, then admits it only if its kind is listed. Never write a deny-list check such as `if kind == Enrollment`. A handwritten route (the feed) keeps an allow-list of kinds beside its handler that mirrors its Protocol security, and a scenario proves it.
- Use the generated constants and `Valid()` methods. Use the generated `nullable.Nullable[T]` when absent and `null` mean different things. Never carry the raw request body through the context.

### Errors

- A module declares its Protocol-visible failures with the `problem` constructors, for example `problem.Conflict("registration_conflict", "The registration identity or facts conflict.")`. The code and message are part of the contract.
- Wrap unexpected errors with context: `fmt.Errorf("read Entity %s: %w", id, err)`.
- Never discard an error. If background work cannot return it, log it with the operation and resource IDs.
- No `panic` or `Must*` on request paths.

### Storage

- Open every database through `storage.Open`, which sets WAL, the busy timeout, foreign keys and private file modes, then applies migrations.
- Store instants as `INTEGER` Unix milliseconds in UTC. RFC 3339 text does not sort correctly when the fractional digits vary.
- Store booleans as `BOOLEAN` so sqlc produces `bool`.
- Store JSON only for opaque payloads that Core passes through, such as Plugin inputs and outputs. Anything Core queries, merges or validates gets real columns.
- Detect constraint violations with `storage.IsConstraint(err)`, not raw SQLite codes.
- Keep transactions inside one module method. If two modules must commit together, one module method accepts a `*sql.Tx` from the other; do not pass callbacks across modules.

### Concurrency and background work

- No bare `go` statements in handlers or modules. Background work belongs to a component with a lifecycle: it takes a context, tracks its goroutines and stops them in `Close`.
- Wake on in-process signals (for example a commit notifier), not polling timers. Poll only state that another process changes, and name the interval as a constant with its reason.
- Every retry loop has a bound. No `for {}` compare-and-set loops without a limit.
- Serialize with transactions or narrow locks. Do not add a module-wide mutex around all reads and writes.
- Give every outbound call a timeout from a named constant.

### Style

- Functions stay short: roughly one screen and one level of abstraction. Split instead of adding comments that separate phases.
- No boolean parameters that switch behavior. Write two functions.
- Name limits and intervals as constants in the owning module, with the reason. Protocol-visible limits are declared in Protocol.
- Use `any`, not `interface{}`. Use generated or declared structs, not `map[string]any`, for any shape Core knows.
- Comments explain why, not what. Delete dead code and unused parameters.
- Error and log messages use CONTEXT.md vocabulary.

## Plugins

- Core never names a specific Plugin. Plugin identity, release, capabilities and input schema come from the Plugin's install manifest. Local management is generic over installed Plugins.
- Plugins reach Core only through the SDK and Protocol. There are no private report routes.
- Shipped Plugins contain no test hooks. Timing and fault control for tests belongs to a separate fixture Plugin under `tests/`.

## SDK (TypeScript)

- Every public method is one call through the shared request helper, which unwraps the `openapi-fetch` result and throws `AtlasError`. Do not repeat error handling per method.
- Protocol facts come from `src/generated`. Do not hand-copy enums, and do not decode opaque values such as cursors.
- Each operation makes one request. Core enforces Dataset boundaries through the `dataset_id` in each write; the SDK does not add discovery round trips around writes.
- Mode-specific behavior (HTTP, full synchronization) lives behind one read interface with one implementation per mode, not `if (this.picture)` in every method.
- Name limits in the options type with documented defaults.

## Tests

End-to-end scenarios are the primary evidence that Atlas works. Integration tests cover faults the public boundary cannot reach. Unit tests are rare.

### End-to-end scenarios produce committed artifacts

- Scenarios live in `tests/e2e/` and run the real Core binary (and real Plugin containers where relevant) with the real SDK and real SQLite. Nothing is mocked.
- Every scenario records a transcript: each step, the wire requests and responses it caused, and the observations it checked. The transcript is written to `tests/e2e/artifacts/<scenario>.md` and committed.
- The runner normalizes only nondeterministic values: allocated IDs become stable labels (`<asset-1>`), times become `<time>`, secrets become `<secret:operator>`, and opaque cursors become `<cursor-N>`. It never normalizes ordering, status codes, missing fields or error codes.
- CI reruns every scenario and fails when a transcript differs from the committed file. Regenerate locally with `ATLAS_E2E_UPDATE=1`.
- The artifact diff is the behavior-change record of a PR. Reviewers read it. An artifact change the PR does not explain is a bug until explained.
- The artifact does not replace assertions. Each scenario still asserts the promise it exists for, with expected values authored independently: `protocol/fixtures` or literals in the scenario. A transcript alone only proves that behavior did not change, not that it is correct.
- One scenario per promise, named after the promise, a handful of steps. Shared setup (building, starting, restarting Core, enrolling an Asset) lives in the harness under `tests/e2e/harness/`, never copied between scenarios.
- Be deterministic: no sleeps. Use barriers such as fixture-Plugin hold and release controls, a delayed feed or a gated fetch. Record concurrent steps in the order they were issued.

### Integration tests

- Use Go integration tests for faults that are unreachable from outside: a crash between two writes, corrupted storage, or an interrupted setup. They use real SQLite in a temporary directory and the module's public methods.
- Name each after the fault it proves. Do not re-test something an end-to-end scenario already covers.

### Unit tests

- Add them only for pure functions whose edge cases are hard to reach end to end, such as a cursor codec. Never mock storage, Core or the SDK transport.

## Pull requests

- Keep one ticket slice per PR. Keep the handwritten diff, excluding generated code and artifacts, under about 800 lines; otherwise split it into a stack.
- Include the artifact diffs. Say which scenarios are new and why any existing transcript changed.
- Before requesting review, check the diff against this file: thin handlers, access declared in Protocol, no Plugin names in Core, no untracked goroutines, no polling where a signal exists, no repeated Protocol facts and a scenario for each promise.
