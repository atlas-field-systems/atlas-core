# Differences from Atlas Modernization

This is the maintained comparison register. It records confirmed successor differences and identifies earlier differences that a later decision withdrew. It records intended behavior and design, not completed implementation. Update it whenever an accepted decision changes something inherited from Atlas Modernization. Existing rows should describe the current decision; ADRs retain decision history.

Baseline: the locally inspected Atlas Modernization snapshot at [`8edee4e2743fbf0f85c16dfe638d9222141cf279`](https://github.com/the-Drunken-coder/Atlas-Modernization/tree/8edee4e2743fbf0f85c16dfe638d9222141cf279), reviewed on 20 September 2026. Source links are pinned to that revision. The successor column links to its authoritative decision or design document. A source observation is not a claim that the old behavior was a defect.

## Carried forward or clarified

These accepted choices must not be misreported as newly introduced behavior. Where no baseline difference is established, the row says so.

| Area | Comparison and current requirement |
| --- | --- |
| Resource pillars and ownership | Entities, Tasks and Objects remain the public pillars. Tracks remain an Entity category. Core defines Commands and Assets execute them. Removing Tool Assets is the specific change recorded above. |
| SDK use and trusted Plugins | Modernization already expects Plugins to use the ordinary full-access SDK without a Plugin capability system or direct storage access. Preserve that approach for user-built Plugins, including access to other sources' operational data and permission to initiate Asset Tasks. All external successor operational API interaction uses the SDK, including Object uploads. Local CLI/TUI administration is internal and uses neither the public API nor SDK. Client-side convenience helpers compose supported APIs; Core retains authorization and domain guarantees. Credential management and system administration remain separate. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-25-plugins-use-full-access-atlas-sdk.md), [current design](system-design.md#sdk-as-the-supported-entry-point). |
| Go, TypeScript and Docker deployment | Modernization already uses Go Core, a TypeScript SDK and Compose-managed services/Plugin containers. Carry those choices forward; the successor runs internal Core modules together and uses a sibling container per installed Plugin. Removing PostgreSQL/MinIO services is recorded in D30–D31; changed lifecycle ownership is D24. [Core source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/go.mod), [SDK source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/packages/sdk/src/client.ts), [deployment source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/docker/docker-compose.production.yml), [Plugin source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/plugins/building_scan/compose.yml), [decision](../adr/0017-deploy-core-and-plugins-as-docker-containers.md). |
| Independent Plugin releases | Modernization already has independent Plugin releases. Preserve that independence; coordinated Core/SDK/Protocol numbering does not include Plugins. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-09-01-plugins-release-independently-from-atlas-core.md), [release decision](../adr/0001-release-core-sdk-and-protocol-together.md). |
| Operational consistency | Preserve coherent state changes and publication, authentication, validation and useful duplicate-request behavior within a run. Retention until Reset does not remove these obligations. The changing module supplies the public representation and synchronization distributes committed changes. This ownership rule is accepted; no generic event framework is required. [Current design](system-design.md#change-publication). |
| Operators, publication and offline use | The successor explicitly requires equally trusted operators, direct publication of detections without a review layer, and installed local operation without internet. No contrary baseline behavior is established here; these are scope constraints, not claimed feature removals. [Operating model](operating-model.md). |
| Field lifecycle: explicit successor scope | Set up Core at the site, connect Assets, and run the mission with Core continuously available. Core Restart, Reset and release updates are outside active missions. Mission continuity across Core restart is excluded. The inspected baseline does not establish an equivalent operational restriction, so this is a scope clarification rather than a claimed removed feature. [Operating model](operating-model.md#field-workflow), [lifecycle decision](../adr/0015-separate-start-stop-restart-and-reset.md). |
| Operation submission and effects: explicit successor scope | SDK retries recover the accepted Operation; deliberate reruns create new attempts. Known effects remain attributable after failure, with no automatic rollback. Plugin-specific rerun handling and external effects remain Plugin responsibilities. No equivalent baseline guarantee is established here. [Decision](../adr/0002-core-manages-installed-plugins.md). |
| Dataset identity: explicit successor scope | Reset changes the dataset identifier; Restart preserves it. SDK clients discard obsolete cached state and pending submissions, and Core rejects old-dataset mutations/work submissions and replay/transfer-resume requests with obsolete handles while allowing dataset discovery. This is the chosen reset boundary, not a claim that all baseline reset behavior was absent. [Decision](../adr/0015-separate-start-stop-restart-and-reset.md). |
| Retained setup compatibility: explicit successor scope | Validate configuration and installed Plugins before operational startup. Report invalid configuration, leave incompatible Plugins installed but disabled, and start compatible enabled Plugins. Publish supported client-version ranges and reject unsupported clients. No automatic configuration conversion is required, and no baseline difference is claimed. [Decision](../adr/0005-allow-compatible-client-versions.md). |
| Access and source credentials: explicit successor scope | Operators have full control. Plugin credentials allow cross-source operational APIs and Task issuance/cancellation, but Plugin installation/configuration and process administration are local CLI/TUI controls, absent from the public API and SDK. Trusted integrations may receive provider credentials; Source Gateway and secret brokering are optional. No further baseline difference is claimed here. [Design](system-design.md#identity-and-access). |
| Full-picture read access: explicit successor scope | Every authenticated SDK client, including Assets, may read all operational data with a valid API key; synchronization remains optional. Per-Asset read authorization filters and the proposed caller-scoped retry/upload ownership additions are not adopted. Asset hybrid filters transmission for bandwidth only, with full-picture reads still allowed. No further source difference is claimed. [Access](system-design.md#identity-and-access). |
| Lifecycle tables: successor contract clarification | Tasks retain six execution statuses with cancellation requests recorded separately, explicit actors/transitions and confirmed terminal outcomes. Operations have a separate lifecycle including Interrupted for unresolved interrupted attempts; retries retrieve the original attempt and reruns are explicit. The full transition comparison with Modernization has not been established; this refines the decisions behind D14–D15 and D21. [Tasks](../adr/0007-reconcile-asset-tasks-after-disconnection.md#task-transitions), [Operations](../adr/0002-core-manages-installed-plugins.md#operation-transitions). |
| Scan completion inputs: successor contract clarification | Require both the assigned Asset's completion report and its declared required ready Objects, in either arrival order. Uploading an Object alone cannot complete a Task. This clarifies D16; no separate source-path vulnerability is claimed. [Completion](../adr/0008-complete-scan-tasks-when-required-results-are-available.md#both-completion-conditions). |
| Cancellation and uploads: explicit successor scope | Task cancellation does not cancel result uploads. A ready result may arrive after confirmed Canceled without reopening the Task. Equivalent baseline handling of in-flight uploads has not been established. [Object decision](../adr/0009-expose-objects-only-when-ready.md#task-cancellation-and-result-uploads). |
| Restart interruption: explicit successor scope | Retain Task outcomes without inferring Asset execution. Classify unfinished Core-owned Operations/transfers as interrupted; no automatic rerun or transfer reattachment. Keep partial content/progress for inspection until Reset. Equivalent baseline outcome classification has not been established. [Lifecycle](../adr/0015-separate-start-stop-restart-and-reset.md#unfinished-work-after-stop-or-restart). |
| Writing-release check: successor enforcement | Ordinary Start refuses a dataset written by another Core release and directs the user through explicit update/Reset. No silent wipe or migration occurs on Start. This enforces the release Reset decision in D08; it does not claim the baseline lacked every version check. [Release check](../adr/0015-separate-start-stop-restart-and-reset.md#release-mismatch-detection). |
| Operational protections: explicit successor scope | Attribute local administration, protect retained credentials, redact secrets from logs/errors and bound requests/uploads/in-flight work. Mechanisms and numeric limits remain open; no baseline absence is claimed. [Protections](system-design.md#basic-operational-protections). |
| Synchronization gaps: explicit successor scope | A client that cannot replay all missed changes must detect that its picture is stale and resynchronize; silent loss cannot leave the picture presented as current. No source defect or new transport choice is claimed. [Synchronization](system-design.md#detectable-synchronization-gaps). |
| Expected workload | Plan for roughly 20 Assets, one or two operators and potentially 100–200 local aircraft Tracks. Thousands of aircraft are a future scale to evaluate. Reporting rates and Object sizes remain unknown. This is a planning target, not evidence of a capacity change. [Workload](operating-model.md#expected-workload). |

## Boundaries of this register

The [stack](../adr/0016-use-go-sqlite-and-openapi-tooling.md) and [Docker organization](../adr/0017-deploy-core-and-plugins-as-docker-containers.md) are selected. Exact tool/spec versions, driver, transfer/streaming mechanisms, private management channel, Plugin manifest/distribution and UI integration remain open. Do not turn research alternatives into accepted differences. The superseded infrastructure-first proposal is successor planning history, not an Atlas Modernization baseline behavior; [ADR-0014](../adr/0014-build-dedicated-atlas-systems.md) records the current dedicated-systems direction.

When recording another difference, verify the old behavior against a named source revision, describe the new observable behavior or ownership rule, and link the accepted decision. If the baseline is unknown, say so rather than claiming a removal. Split distinct behavior changes into separate rows and preserve existing row IDs when updating them. This register covers comparisons identified so far and must grow as further differences are accepted. Retain stable IDs for withdrawn differences and label their current disposition rather than continuing to count them as differences.
