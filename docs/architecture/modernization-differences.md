# Differences from Atlas Modernization

This is the maintained register of confirmed successor differences. It records intended behavior and design, not completed implementation. Update it whenever an accepted decision changes something inherited from Atlas Modernization. Existing rows should describe the current decision; ADRs retain decision history.

Baseline: the locally inspected Atlas Modernization snapshot at [`8edee4e2743fbf0f85c16dfe638d9222141cf279`](https://github.com/the-Drunken-coder/Atlas-Modernization/tree/8edee4e2743fbf0f85c16dfe638d9222141cf279), reviewed on 20 September 2026. Source links are pinned to that revision. The successor column links to its authoritative decision or design document. A source observation is not a claim that the old behavior was a defect.

## Confirmed differences

| ID and area | Atlas Modernization baseline | Atlas Core successor |
| --- | --- | --- |
| D01: Repository boundary | Core is under `services/core`, SDK and Protocol under `packages`, with other products in the same repository. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/README.md) | The successor places the Core system in an `Atlas Core/` folder with sibling SDK/Protocol deliverables. Command Interface stays outside the Core system. [Outline](system-outline.md#what-is-decided) |
| D02: Coordinated release | The inspected Core release workflow packages the server image and CLI; SDK has its own package version and Protocol has a schema revision. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/.github/workflows/release-atlas-core.yml) [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/packages/sdk/package.json#L1) | One workflow releases Core, SDK and Protocol with the same version, including unchanged components. Plugins retain independent releases. [Decision](../adr/0001-release-core-sdk-and-protocol-together.md) |
| D03: Generated API coverage | The generator output list contains contract types/validators, catalog and revision artifacts; SDK calls and Core routes are separately authored. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/packages/protocol/tools/internal/artifacts/manifest.go#L70) | Protocol describes public operations and observable guarantees as well as resource shapes. Generate suitable SDK calls and Core bindings, while keeping business behavior handwritten. [Decision](../adr/0011-generate-shared-contracts-with-minimal-customization.md) |
| D04: Generator upkeep | Go types are authored in a generated-path file, with explicit projection overrides in the custom generator. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/packages/protocol/tools/internal/artifacts/go_contracts.go#L18) | Prefer supported output and minimal configuration; avoid manual output edits, endpoint-specific templates and duplicate wrappers. The toolchain remains undecided. [Decision](../adr/0011-generate-shared-contracts-with-minimal-customization.md) |
| D05: Runtime compatibility | SDK rejects any Protocol revision different from its embedded revision. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/packages/sdk/src/feed-connection.ts#L332) | Allow different release versions when contracts are compatible. Exact compatibility rules remain to be designed. [Decision](../adr/0005-allow-compatible-client-versions.md) |
| D06: SDK structure | Ordinary resource methods delegate to `SyncEngine`; full-picture synchronization is already optional. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/packages/sdk/src/client.ts#L120) | Keep every consumer on the SDK, with basic API access that does not require synchronized-replica machinery and optional maintained-picture behavior. The change is the separation of responsibilities, not the invention of optional sync. [Design](system-design.md#sdk-as-the-supported-entry-point) |
| D07: Operational retention | Production resource rows and Object content survive restart; explicit scratch mode clears them. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/README.md#L4) | Every Core start clears operational records, content, history, transfer state and synchronization records. Installed Plugin selections, credentials and configuration survive. [Decision](../adr/0013-start-each-core-run-with-empty-data.md) |
| D08: Schema evolution | Startup applies an ordered migration ledger, including before a scratch reset. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/database/db.go#L268) | Initialize the current operational schema from empty storage. No version-to-version operational-data migrations or backup/restore requirement. [Decision](../adr/0013-start-each-core-run-with-empty-data.md) |
| D09: Restart/reset interface | CLI exposes separate `restart` and `reset` commands. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/surfaces/core-cli/src/application.ts#L177) | Restart includes reset. There is no preserve-data restart mode. Core is assumed to stay running while Assets operate; cross-restart continuation is outside scope. [Decision](../adr/0013-start-each-core-run-with-empty-data.md) |
| D10: Activity history | The trusted-Plugin decision explicitly excludes Plugin provenance/audit records; Task idempotency is not actor provenance. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-25-plugins-use-full-access-atlas-sdk.md#L6) [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/atlas-protocol/commands-and-tasking.md#L300) | Keep actor-attributed activity history for Task issuance/cancellation and Plugin, credential and configuration changes during the current run. Do not retain it across Core starts. [Outline](system-outline.md#consequences-of-the-lifecycle-and-history-decisions) |
| D11: Immediate-start deadline | Core fails an immediate Task when its start report arrives outside the 60-second window. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/actions/task_transition.go#L64) | Remove the inherited 60-second rule. Execution scheduling belongs to the Asset OS. [Decision](../adr/0007-reconcile-asset-tasks-after-disconnection.md) |
| D12: Queue policy | Core defines queued/immediate scheduling, permits one queued Task in progress, and gates ordered delivery. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/atlas-protocol/commands-and-tasking.md#L262) [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/actions/task_runtime.go#L405) | Asset OS owns queue order, scheduling, execution and interruption. Core records instructions/outcomes and validates its own lifecycle guarantees. [Design](system-design.md#core-tasking-and-asset-execution) |
| D13: Task creation eligibility | Task creation requires a registered, ready execution runtime and resolves its scheduling declaration. This check is not itself proof that every disconnected Asset is rejected. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/actions/task_create.go#L83) | Support issuing valid Tasks to disconnected Assets. Do not inherit live execution readiness as a prerequisite for recording operator or Plugin intent. Target and Command validation remain. [Decision](../adr/0007-reconcile-asset-tasks-after-disconnection.md) |
| D14: Cancellation acknowledgement | `cancelTask` immediately writes terminal `cancelled` and a finish time; the old lifecycle has six main statuses. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/actions/task_transition.go#L234) | Add Cancellation requested. Record Canceled after Asset confirmation; preserve the seven agreed statuses. [Decision](../adr/0007-reconcile-asset-tasks-after-disconnection.md) |
| D15: Late completion after cancellation | Completion requires In progress except for repeat-terminal handling; an already-cancelled Task cannot complete through that path. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/actions/task_transition.go#L125) | Accept completion reported before the Asset learned of cancellation when its result requirements are met. Retain the cancellation attempt in activity history. [Decision](../adr/0007-reconcile-asset-tasks-after-disconnection.md) |
| D16: Scan completion promise | Generic completion validates Command output and records Completed; that function does not establish the successor-specific ready scan-Object promise. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/actions/task_transition.go#L149) | A scan is Completed only once its required result is available. While uploading, retain In progress and allow separate Asset-provided detail. Later Plugin processing does not hold the scan Task open. [Decision](../adr/0008-complete-scan-tasks-when-required-results-are-available.md) |
| D17: Public storage locations | ObjectResource contains `bucket` and `path`. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/packages/protocol/schema/jsonschema/atlas.schema.json#L1480) | Keep physical storage locations private. Clients use Object identity and SDK/Core content APIs. [Design](system-design.md#objects-hide-storage) |
| D18: Object availability | A metadata-only Object can be created and published independently of content upload. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/actions/object_actions.go#L91) | Do not publish an unavailable placeholder for content still uploading. Publish once ready for use. [Decision](../adr/0009-expose-objects-only-when-ready.md) |
| D19: Interrupted uploads | The public upload handler accepts one multipart file request, without a client resume checkpoint in that contract. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/api/handlers/handler_object_transfer.go#L144) | Large uploads resume from confirmed progress after connection loss within the same Core run. Partial state remains private and is wiped on Core restart. [Decision](../adr/0009-expose-objects-only-when-ready.md) |
| D20: Taskable Plugins | Plugins can advertise a Tool Asset ID; work outliving an Operation request is directed to Tool Tasks. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-24-core-owns-plugin-http-interface.md#L4) | Plugins are never Task targets. Plugin processing uses Operations. Plugins may issue existing Commands as Tasks to actual Assets through the SDK. [Decision](../adr/0004-core-owns-commands-and-assets-execute-tasks.md) |
| D21: Operation lifetime | Invocation derives its execution context from the caller; disconnect cancels the private request. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/plugins/registry.go#L155) [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-24-core-owns-plugin-http-interface.md#L4) | Accepted Operations have an identifier and queryable state/outcome and continue after caller disconnection. Cancellation is explicit. [Decision](../adr/0002-core-manages-installed-plugins.md) |
| D22: Operation duration | Core caps Operation timeouts at 25 seconds. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/services/core/internal/plugins/registry.go#L16) | Remove this inherited universal cap. Support long processing through the Operation lifecycle; specific limits remain implementation choices. [Design](system-design.md#plugin-operations) |
| D23: Operation side effects | The old Operation contract is synchronous and side-effect-free; writes/outliving work belong elsewhere. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-24-core-owns-plugin-http-interface.md#L4) | Plugin processing may publish results through normal SDK operational APIs. Do not impose the old read-only Operation contract. [Decision](../adr/0004-core-owns-commands-and-assets-execute-tasks.md) |
| D24: Plugin lifecycle owner | The host deployment orchestrator/CLI owns installation and process lifecycle; Core connects to configured endpoints and has no installation API. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-25-compose-manages-plugin-containers.md#L4) | Core manages installed Plugin lifecycles and exposes their management capabilities. Process/container mechanism remains undecided. [Decision](../adr/0002-core-manages-installed-plugins.md) |
| D25: Plugin changes while Core runs | Cached manifests are replaced on Core restart; the source decision explicitly requires Core restart for changed manifests. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-25-core-connects-to-configured-plugins-over-http.md#L6) | Install, update, remove, enable and disable Plugins without restarting Core or interrupting unrelated Plugins and Asset connections. Planned changes wait for active work to finish or be explicitly cancelled. [Decision](../adr/0006-protect-active-plugin-work-during-lifecycle-changes.md) [Decision](../adr/0002-core-manages-installed-plugins.md) |
| D26: Plugin fault handling | The shipped Building Scan Compose configuration uses `restart: unless-stopped`. This is evidence for that deployment, not every Plugin. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/plugins/building_scan/compose.yml#L19) | Fault reporting and operator-requested restart are sufficient. Automatic restart is not required; restarting a Plugin does not automatically rerun a failed Operation. [Decision](../adr/0002-core-manages-installed-plugins.md) |

## Carried forward or clarified

These accepted choices must not be misreported as newly introduced behavior. Where no baseline difference is established, the row says so.

| Area | Comparison and current requirement |
| --- | --- |
| Resource pillars and ownership | Entities, Tasks and Objects remain the public pillars. Tracks remain an Entity category. Core defines Commands and Assets execute them. Removing Tool Assets is the specific change recorded above. |
| SDK use and trusted Plugins | Modernization already expects Plugins to use the ordinary full-access SDK without a Plugin capability system or direct storage access. Preserve that approach for user-built Plugins, including access to other sources' operational data and permission to initiate Asset Tasks. All external successor consumers are expected to use the SDK. Credential management and system administration remain separate. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-08-25-plugins-use-full-access-atlas-sdk.md), [current design](system-design.md#sdk-as-the-supported-entry-point). |
| Independent Plugin releases | Modernization already has independent Plugin releases. Preserve that independence; coordinated Core/SDK/Protocol numbering does not include Plugins. [Source](https://github.com/the-Drunken-coder/Atlas-Modernization/blob/8edee4e2743fbf0f85c16dfe638d9222141cf279/docs/design-decisions/2026-09-01-plugins-release-independently-from-atlas-core.md), [release decision](../adr/0001-release-core-sdk-and-protocol-together.md). |
| Operational consistency | Preserve coherent state changes and publication, authentication, validation and useful duplicate-request behavior within a run. Disposable data does not remove these obligations. Shared change-publication implementation guidance is still provisional. [Current design](system-design.md#change-publication). |
| Operators, publication and offline use | The successor explicitly requires equally trusted operators, direct publication of detections without a review layer, and installed local operation without internet. No contrary baseline behavior is established here; these are scope constraints, not claimed feature removals. [Operating model](operating-model.md). |
| Expected workload | Plan for roughly 20 Assets, one or two operators and potentially 100–200 local aircraft Tracks. Thousands of aircraft are a future scale to evaluate. Reporting rates and Object sizes remain unknown. This is a planning target, not evidence of a capacity change. [Workload](operating-model.md#expected-workload). |

## Boundaries of this register

Language, database, storage backend, generator, transport details, Plugin packaging and Plugin UI integration are not selected. Do not turn research alternatives into accepted differences. The superseded infrastructure-first proposal is successor planning history, not an Atlas Modernization baseline behavior; [ADR-0014](../adr/0014-build-dedicated-atlas-systems.md) records the current dedicated-systems direction.

When recording another difference, verify the old behavior against a named source revision, describe the new observable behavior or ownership rule, and link the accepted decision. If the baseline is unknown, say so rather than claiming a removal. Split distinct behavior changes into separate rows and preserve existing row IDs when updating them. This table covers the confirmed differences identified so far and must grow as further differences are accepted.
