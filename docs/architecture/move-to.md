# Move To implementation

Ticket #8 implements one Protocol Command, `move_to`. Its input is a latitude and longitude in degrees. The Command Catalog is authored in `protocol/command-catalog.json` and copied into the SDK's generated local catalog and Core's embedded validation catalog. Protocol also owns the request and response schemas in `protocol/openapi.yaml`. Assets advertise `move_to` with `queued` scheduling; Core rejects unknown Commands and unsupported scheduling when an Asset enrolls, updates its manifest, or receives a Task.

`POST /tasks` accepts an explicit Dataset ID and a caller-persisted submission UUID. Core stores a digest of the original request, an immutable Task assignment, typed destination coordinates, the Asset's declared cancellation/progress support, and the next per-Asset acceptance sequence in one SQLite transaction. A matching retry returns the current Task without allocating another sequence. A changed retry conflicts. Asset contact or busy status does not gate acceptance. Task IDs and acceptance sequences survive same-release Restart until Reset.

`GET /tasks` pages in creation-commit order. `GET /entities/{entity_id}/tasks` pages in that Asset's acceptance order and includes pending, cancellation-requested and terminal Tasks. Reads do not acknowledge delivery. The Asset OS executes work; Core does not start or schedule it.

`PATCH /tasks/{task_id}/status` is the shared lifecycle route. Protocol separates cancellation, progress-only reports and one execution-report shape per status. Operators and managed Plugins can request cancellation using a stable request UUID when the Asset declared cancellation support. The Task remains `cancellation_requested` until its assigned Asset confirms that UUID. The assigned Asset reports acknowledgement, start, progress, completion or failure using a report UUID and increasing Asset report sequence, shared with its other reports. Progress values require advertised support; a progress-only report omits `status`. Fresh reports update Asset contact and its change record in the same transaction as any Task change. Matching report-ID retries do not refresh contact or add changes. A new report confirming an already terminal outcome refreshes Asset contact without changing the Task. Terminal outcomes cannot change. Task issuance and cancellation activity commits with the Task change.

Ticket #9 retains the latest explicitly reported acknowledgement or start as `execution_status`, independently of `cancellation_requested`. A later acknowledgement cannot move a reported start backward. Progress and terminal outcomes keep that execution fact, and a completion or failure may settle a Task before cancellation is confirmed. An absent `execution_status` means Core received neither report; Core does not infer a start from a completed Task or from disconnection. On reconnect, the Asset reads every assigned page in acceptance order, reports established offline outcomes, and reconciles remaining Task intent with its onboard queue. Core does not execute historical Tasks on the Asset's behalf.

Every Task response includes the Dataset ID and `change_sequence`; `created_sequence` stays fixed at creation. The SDK returns when Core commits. A fresh report that confirms an already terminal outcome commits only Asset contact, so that write response also carries `receipt_sequence` for the later contact change. A matching report retry returns a sequence that covers the original contact; it may reflect newer Asset contact. In full synchronization mode, `waitForSynchronization` waits for `receipt_sequence` when present and otherwise waits for `change_sequence`. An HTTP client has no local coverage and cannot use the wait. The full snapshot pages Entities first, then Tasks under one baseline. Each change carries exactly one payload matching its resource type. Replay and feed use the same ordered change log, so a later Task response or feed event cannot skip an earlier Entity or Task change. A snapshot page can contain a newer resource version than its baseline; replay advances through such changes without emitting them again as local changes. A rebuild can satisfy a pending wait once its baseline covers the commit, provided the Dataset identity still matches.

The remaining Task controls, queue revisions, Asset hybrid scope and Object-backed results belong to their dependent slices. The current Move To Task needs no Object or Plugin to finish.

The existing `reports-and-the-change-log-survive-restart` transcript changed because full-picture pages now include an empty `tasks` array and a continuation into Task snapshot pages, even when the Dataset has no Tasks.
