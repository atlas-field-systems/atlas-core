# Testing strategy

## End-to-end workflows first

Accepted on 27 September 2026. Default to end-to-end tests of complete workflows through supported interfaces, using the real components involved. These tests are the primary evidence that a feature works, including relevant failure and recovery paths. Add focused integration or unit tests only when they provide useful coverage that those workflows cannot exercise effectively, and explain that benefit. Do not require a unit test for every function or duplicate workflow assertions at every layer.

For Atlas Core, end-to-end coverage includes SDK-to-Core workflows and local management workflows, with real storage and relevant Plugin containers. Simulated Assets provide controlled execution and fault inputs for the Core contract milestone. Browser automation and physical hardware are not prerequisites for that milestone; real Asset and radio claims require the later evidence described below.

Start feature coverage with a complete workflow and its observable outcome, then extend it for relevant failures and retries. Operation-by-operation parity checks support that coverage but cannot alone prove that the composed workflow succeeds. The [MVP integration checks](architecture/system-design.md#mvp-integration-checks) give the initial workflow examples.

## SDK and Core integration requirements

Accepted on 22 September 2026. Atlas requires extensive integration testing between the real SDK and Core. External systems are expected to integrate through the SDK; demonstrating its behavioral parity with Core makes those external SDK tests useful evidence about Core integration. Cover the contracts thoroughly with independent expected outcomes, rather than maximizing test count or testing generated code against another output of the same generator.

This is a required testing plan. The repository currently contains documentation, not an implemented suite or measured parity result.

## Real boundaries and independent expectations

Run the actual supported TypeScript SDK against the actual Go Core over its public HTTP/feed boundary, using real SQLite and temporary Object storage. Include the real Plugin container boundary where relevant. Simulated Assets and deterministic fault injection provide reproducible inputs; mocked Core responses alone cannot satisfy these integration requirements.

Run shared, independently authored scenario fixtures through both direct Protocol requests and public SDK methods against equivalent isolated initial datasets. Check expected requests, responses, errors, stored outcomes and observable changes. Normalize only intentionally nondeterministic fields such as allocated IDs or clock values; do not normalize away ordering, missing fields, errors or duplicate effects. Direct HTTP is a test oracle path, not a bypass added to synchronized SDK application methods.

Parity means equivalent specified behavior for corresponding operations. The general SDK has HTTP and full-synchronization modes under [ADR-0020](adr/0020-limit-general-sdk-to-http-and-full-sync.md). At defined synchronization boundaries they must agree on resource values, lifecycle outcomes and deletions. Tests must also prove their different source and freshness rules, including not-ready/stale behavior, local queries/feed and the absence of hidden HTTP read fallback. Core per-Asset snapshot, feed and replay coverage is deferred, so Asset hybrid is not a current test target. Match supported Core/SDK/Protocol combinations and test explicit rejection of unsupported combinations; version coverage must be recorded.

## Core contract and field validation milestones

Accepted on 23 September 2026: distinguish evidence about Core from evidence about real Asset behavior. The initial MVP uses a simulated Asset to verify Core/Protocol/SDK contracts against real APIs and storage. It can establish correct Task delivery and handling of reported outcomes under the tested conditions; it cannot prove that physical movement or device-side recovery is correct.

Before claiming field readiness for an Asset integration, exercise a real Command through its real Asset runtime and hardware, including lost contact, cancellation and process restart with uncertain work. Verify actual execution and outcome reporting together. This later milestone does not add an Asset OS to Core or block the simulated MVP. Physical radio claims additionally require the [radio evidence](#external-systems-and-future-radio-gateways) below.

Separately prove extension independence with a Plugin built in its own repository using the supported SDK and container contract. Install and invoke it, stop and remove it while Core remains usable, inspect its retained Operation results, and archive the extension source without adding it to Core's normal build dependencies. A small Plugin may start in this repository for the MVP; that alone does not pass the independent-extension milestone.

## Required scenario coverage

| --- | --- |
| Every public SDK operation | Successful operation, meaningful validation failures, absent/null/partial-field behavior, errors, pagination, request identity and response mapping against Core. Unsupported or deliberately unwrapped routes are listed explicitly. |
| Asset identity and contact | Deployment-authorized automatic enrollment without per-Asset approval, enrollment retries after lost responses, subsequent Asset edits and Restart; conflicting/concurrent retries, credential association and deleted-Asset retries; two distinct Assets, valid own reports and rejected cross-Asset reports across every mutation path; fresh reports versus duplicates/stale reports, including fresh queue adoption/conflict reports updating heartbeat and its Entity feed change together with queue state, duplicate/historical queue reports leaving contact unchanged and operator reorder requests never establishing Asset contact; administrative boundaries and revocation, including already-open feeds, buffered-event races and reconnect rejection. |
| Asset retirement | Exercise every [ADR-0019 workflow](adr/0019-retire-assets-without-inventing-task-outcomes.md#required-implementation-evidence) through the real SDK and Core: retirement with disconnected/nonterminal work, retained evidence and protected results, assignment/report/provisioning races, revocation of open feeds, all SDK modes, retry deduplication/conflict/deleted-result handling, Restart and obsolete-Dataset rejection. After Reset, reject fresh registration of the retired ID even with the same principal and current enrollment authorization. |
| Asset deletion | Rejected deletion with nonterminal Tasks leaves credentials usable; allowed deletion atomically revokes every bound credential and closes feeds. Reject subsequent reads/reconnects/reports, preserve revocation through Restart/Reset, and exercise concurrent credential provisioning, registration retries and Task assignment without losing retained history. With the new Task still nonterminal, assignment committing first makes deletion fail; deletion committing first makes assignment fail. |
| API-key creation | Prepare and retain the secret before submission; lost success response and concurrent retries produce one usable credential; conflicting initial facts fail, revoked-key retries never reactivate it, ordinary Reset retains creation state while obsolete-Dataset requests fail, and no response/list/log exposes a secret. |
| Task lifecycle | Accepted transitions and rejected transitions, cancellation requested versus confirmed, completion/failure races, duplicate and out-of-order reports, late Object readiness, terminal immutability and no inferred outcome from disconnection. Confirm Asset/Task pause from actual reports; distinguish successful Pause from merely accepted request, retain cancellation intent during suspension and reject stale reports that would resume or reopen work. |
| Immediate Commands and Pause | Lights execute alongside Move To without changing the queued path; supported dual-mode Commands can also queue. Pause interrupts a running Task, completes its own control Task once applied, and leaves the Asset and interrupted Task paused without draining the queue. Include no-current-Task Pause, failure to pause, duplicate Pause after completion, independent actions while paused, separate/out-of-order status reports, and unsupported scheduling. Resume continues the same interrupted Task before the queued path, unsafe-to-resume work reports failure, no-current-Task Resume releases the queue, terminal/cancellation outcomes are not bypassed, and duplicate or late reports cannot apply Pause/Resume again. Test valid/expired immediate delivery, no universal timeout, newer Pause/Resume beating delayed older controls without rolling back reported state, and failed resumption retaining pause until a new explicit Resume. Specify concrete clock-boundary fixtures with the wire contract. |
| Task queues | Concurrent edits from the same revision, idempotent edit retries, delayed confirmations, new Tasks and execution starts during reordering, reconnect reconciliation, rejection of edits containing unstarted `cancellation_requested` or terminal `completed`, `failed` or `cancelled` Tasks while preserving requested and confirmed order, no reordering of started work including paused Tasks and no Core scheduling gate based on communications. HTTP reads and the full synchronized picture expose coherent requested/confirmed revisions; pagination and replay cannot present mixed revisions as a confirmed queue. |
| SDK modes | Identical public operational read methods in HTTP and full synchronization; HTTP passthrough; full local picture and local query/feed behavior; writes to Core and authoritative local reconciliation. Assign a Task referencing a moving Track and verify its subsequent telemetry reaches the full picture without application polling or Task reissuance, including after reconnection. The full picture retains unrelated resources too; terminal Tasks remain available after rebuilding until Reset. |
| Synchronization | Initial pagination while writes occur, feed/recovery handoff, disconnects, duplicate/delayed events, deletion replay, expired cursors, slow consumers and bounded buffers. Prove no silent gaps, duplicate notifications or cursor advancement past unapplied changes. Deliver a successful write response at N+2 before N+1: the write returns Core's result immediately, while picture reads and local feed/history retain ordered application. Cover response/feed arrival in both orders: a response alone changes no picture state, local history, notification or cursor; only snapshot/feed/replay advance the picture. Include multi-resource commits, later update/deletion and replay expiry. Interrupt the feed after commit and verify write success remains valid, picture status reports interruption and the mutation is not resubmitted. Reset during reconciliation must not insert an old result into the new Dataset. |
| Asset-process recovery | Reconcile retained Tasks before execution; completed physical work is not repeated, uncertain work holds queued continuation, and obsolete process reports cannot rewrite reconciled state or reclaim authority through a repeated hello. Deliver later telemetry before an unrecorded Task outcome and verify the outcome is not discarded solely for its lower sequence; a new sequence alone must not establish fresh contact for historical traffic. Ordinary same-process reconnect is tested separately. |
| Reset and Restart | Old responses, submissions, retries and cursors rejected after Reset in every mode; no obsolete state resurrection; retained Dataset ID/writing release, Task creation retry identities, Entity identity reservations, Asset report acceptance state and change window after Restart; duplicate or delayed check-in/component/status/Task lifecycle/queue adoption or conflict reports cannot refresh contact or overwrite retained newer data; after Reset, a different principal or Entity type cannot claim a retained bound Asset ID, the original nonrevoked identity can explicitly re-register with fresh authorization/request identity, and old credentials cannot report as a replacement; refusal on writing-release mismatch; interrupted Operations without automatic rerun. |

| Objects and histories | Interrupted full-file upload and cleanup; crashes before and after the ready-state SQLite commit, with durable content first, safe orphan cleanup and no success inferred from files alone; an immediate whole-file retry without Restart after pre-commit failure, using a fresh private attempt location while preserving files owned by committed Objects, active attempts or unknown owners; lost success response, concurrent identical retries, conflicting identity reuse, ready-only visibility, immutable bytes, download equality, SDK-allocated result IDs with report-before-upload and upload-before-report, conflicting ID claims, deleted-upload retries without resurrection, required-result protection from declaration acceptance before and after upload, preserved through completion/failure/cancellation, deletion conflicts without optimistic SDK removal, metadata-association edits that cannot release protection, shared required Objects, declaration/publication/deletion races, rejection of declarations for deleted IDs without accepting an unsatisfiable completion report, protection retained across Restart and cleared on Reset, movement deduplication and stable history pagination, deleted Asset/Track history reads with deletion indicators, empty intervals versus never-present IDs, obsolete-Dataset history rejection, rejected Entity ID reuse after deletion across Restart with original history/Task/Object associations preserved, activity attribution surviving profile/credential deletion without secrets. |
| Plugin Operations | Durable acceptance before dispatch, disconnected caller, duplicate submission, progress/cancellation/terminal races, failure with known outputs, Plugin loss/removal and Core interruption. | Plugin operational storage | Through real local management and a Plugin container, write files and private SQLite working state in the managed operational directory. Reset clears them, including disabled or faulted Plugins' directories, while retaining Plugin settings, credentials and reference data. Buffered outputs and queued work from the old Dataset cannot republish after startup. Interrupt cleanup and make cleanup fail, then retry: the failure remains explicit, no fresh Dataset is established and Plugins remain stopped until cleanup succeeds. Use sequence-driven tests with an independently specified state model for lifecycle and recovery combinations. Preserve failing seeds and packet schedules so randomized failures can be reproduced. Apply the [workflow-first policy](#end-to-end-workflows-first) when choosing focused tests; the transition-module case below supplements the required real integration coverage.

## Fault and bandwidth testing

Use the interface as the test surface for the [ownership choices](planning-reconciliation.md#module-ownership-decisions-26-september-2026). Exercise interrupted lifecycle actions through shared local management, interrupted Object publication through Objects and Restart, and picture ordering through SDK reads, queries, subscriptions and status. Keep real Docker, SQLite and files in the relevant integration checks. Private fault-injection adapters may schedule failures, but do not replace those checks with assertions about helper call order. Reuse the scenarios above rather than creating a second suite for the module arrangement.

Exercise shared Asset report acceptance through Entity and Task reporting against real SQLite: report acceptance facts, Task changes, contact and change records commit together or remain unchanged on failure; duplicate reports do not refresh contact. Verify behavior through the supported interfaces rather than inspecting shared-helper calls.

Close the reporting contract in the first Asset reporting workflow. Interleave Task reports that update Entity contact, partial telemetry reports and descriptive edits under the selected version-precondition policy. Prove that unrelated contact changes do not cause silent loss or stale overwrite, and verify the specified conflict behavior. Use concrete freshness and clock-uncertainty fixtures to distinguish a new current report from newly delivered historical traffic. The process-recovery workflow must exercise its authority-transfer proof with concurrent replacement attempts, a lost transfer response and an obsolete process sending another hello. Reuse the identity/contact and Asset-process recovery scenarios above; do not add a separate acceptance suite.

For the [Asset ownership follow-up](planning-reconciliation.md#asset-ownership-follow-up), extend the shared acceptance scenarios with a failure before commit and a retry after Restart. Deliver newer telemetry before an unrecorded Task outcome without losing the outcome or treating historical traffic as fresh contact. Exercise deletion through the existing Entity interface, including both commit orders against Task assignment, concurrent credential provisioning, and buffered feed delivery at revocation. Race deletion against in-flight Entity and Task reports that have already passed initial authorization. If deletion commits first, reject the report without recording acceptance, domain effects or changes. If the report commits first, commit all its valid effects together before deletion reevaluates the nonterminal-Task guard; remaining nonterminal work still prevents deletion. Keep these checks in the existing Asset deletion and reporting scenarios.

The [second-review ownership choices](planning-reconciliation.md#module-ownership-decisions-second-review-26-september-2026) add these test surfaces, again reusing the scenarios above:

- Asset report acceptance: drive accepted, duplicate and rejected dispositions through every reporting route, and verify that a previously unrecorded historical outcome sent as the newest report after reconnection is recorded without refreshing contact, including obsolete process generations and operator attempts to submit Asset-reported components.
- Task transitions: run state-model sequences, including delayed Pause/Resume reports against newer applied control intent and results arriving in both orders, through the pure transition module without SQLite. This focused suite explores combinations that are costly to enumerate through complete workflows. It proves transition decisions only; the required workflows still exercise persistence, delivery, retries and recovery through real Core and SDK interfaces.
- Write commits and retry identity: obsolete-Dataset rejection at the commit, including API-key creation and credential revocation requests delayed across Reset; first and replay claims for every retry kind under concurrent identical requests; conflict claims when the same identity is reused with different original facts; and ended claims for the kinds whose results can later be deleted or revoked (registration and retirement after Asset deletion, upload after allowed Object deletion, and API-key creation after revocation).
- Dataset opening: crash each module's state, then open retained; interrupt Reset at each step, including partway through old-content removal and after Core serves but before Plugins start, and verify the next Start completes it without leaving content from any earlier Dataset or clearing post-Reset data; import the local activity journal twice without duplicate records, import first-time setup actions into the first Dataset, and crash after a Reset is established without importing pre-Reset entries.
- Asset client: registration retries across an Asset process restart using the retained identity, required-result uploads in both arrival orders, reconnect reconciliation and recovery from supplied execution evidence against real Core. Build the simulated Core-facing Asset client on the SDK helper; a gateway uses the same helper while its separate device integration supplies Asset-originated evidence.
- Required-result holds: when all required uploads precede the completion declaration, complete the Task in the declaration/hold commit using the already-published Objects. When the declaration precedes the last required upload, complete the Task in that Object's publication commit. Both paths obey the terminal-state rules.

Inject dropped requests, lost successful responses, reconnects, duplication, reordering, latency and bandwidth limits at appropriate transport boundaries. Use deterministic barriers and observable readiness rather than arbitrary sleeps. Include targeted crashes between accepted database writes and delivery to verify recovery behavior. Keep test fixtures isolated and resettable.

Measure steady telemetry, Task delivery/cancellation/reordering, initial full synchronization and reconnection separately. Compare HTTP and full synchronization on representative Core-facing IP workloads. Account for metadata, authentication overhead, acknowledgements and retries, not only useful JSON bytes. Measure the constrained gateway-to-Asset link separately when that integration exists. Set byte/latency/memory budgets from representative measured workloads before claiming a performance guarantee. Load tests must report correctness failures as well as throughput; a faster run with lost updates does not pass.

## External systems and future radio gateways

Publish reusable contract scenarios and expected outcomes that Core-facing IP consumers exercise through the SDK. A gateway uses HTTP or full synchronization over an adequate IP link to Core; it may run wherever that link is available, without a same-host or same-LAN requirement. Constrained transport belongs between the gateway and Assets. Device runtimes and radio transport remain separate from the general SDK, which is not required on firmware. See [ADR-0020](adr/0020-limit-general-sdk-to-http-and-full-sync.md).

For a radio gateway, use the same logical fixtures for firmware-to-gateway translation and gateway-SDK-to-Core behavior. Preserve identity, units, optional values, request/report identity, lifecycle ordering, errors and Dataset boundaries through encoding and decoding. A gateway's live Core connection must not turn an Asset's delayed report into fresh Asset contact or authorize that gateway to invent execution evidence.

SDK–Core parity plus firmware–gateway parity provides composable evidence only for the versions, supported operations and conditions covered. Keep a representative end-to-end suite through firmware or a faithful emulator, the gateway, the real SDK and real Core. Translation boundaries and interacting retries can fail even when each isolated pair passes. Physical radio tests remain necessary for claims about actual RF behavior; emulator results must be labeled as such.

Do not require raw HTTP JSON over a future constrained radio link. Compact representations can preserve the same contract, but must pass the semantic scenarios and measured bandwidth tests. No future gateway or firmware implementation is selected by this testing requirement.

## Continuous integration and completion evidence

Apply the [conventions for preserving checks](agents/code-conventions.md#review-and-maintenance) to test code, fixtures, runner configuration and CI selection. A corrected expectation must cite the governing specification or authorized behavior change; the implementation's current output alone is not an oracle. When replacing or removing a test, identify how its required guarantees remain covered or cite the authorization removing them. If an assertion never represented required behavior, demonstrate that against the governing specification. Preserve required failure and recovery coverage when restructuring suites.

As features are implemented, their contract scenarios ship with them. Require the deterministic SDK–Core integration suite and compatibility checks for relevant changes; group tests for useful feedback without skipping failures. Run broader randomized, sustained-load and impairment matrices on scheduled runs and before releases. Record exactly which suites and version combinations ran; unrun coverage is not a passing result.

A feature is complete only when its applicable end-to-end workflows and required real integration scenarios pass, including relevant failure and retry paths. Reviewers check the observable outcomes those tests establish and the additional coverage any focused tests provide. Preserve reproducible fixtures, failing seeds, versions and useful traces as test artifacts without credentials. Add regressions for demonstrated contract failures, not duplicate smoke tests or snapshots that merely mirror implementation. Exact CI jobs, tooling and numeric workload budgets follow the implementation.
